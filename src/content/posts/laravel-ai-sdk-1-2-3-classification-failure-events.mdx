Your embeddings job died at 3 a.m. and the only trace is a stack trace in the log, because the SDK fired `GeneratingEmbeddings` and then nothing. Your streamed support agent calls a structured sub-agent and gets back "Agent failed: Streaming structured output is not currently supported." Two patch releases in two days close both gaps.

- **1.2.2** (Oct 14, 2026) dispatches `EmbeddingsFailed`, `ImageFailed`, `AudioFailed`, `TranscriptionFailed`, `RerankingFailed` and `ClassificationFailed`, once per failed attempt, failover included.
- The `openai-compatible` driver can classify now. Set `models.classification.default` for it, there is no built-in default.
- **1.2.3** (Oct 15) lets TypeSafe and OpenRouter classify **image attachments**, each in its own wire format, and keeps image names across failover.
- Structured sub-agents inside a streamed parent run through `handle()` instead of failing. A failed turn keeps the tool call id, so OpenAI conversations recover. Laravel 12 conversations keep string ids.

</TLDR>

| Change | Version | PR | Why you care |

## Failure events for every model operation

Since 1.0 the SDK has dispatched a *starting* and a *done* event around each operation: `GeneratingEmbeddings` and `EmbeddingsGenerated`, `Classifying` and `Classified`, and so on. Agents had `AgentFailed`. Everything else had nothing on failure, so a listener that opened a span or a billing row could never close it.

1.2.2 adds one failure event per operation:

| Operation | Starting | Done | **Failed (new)** |
|---|---|---|---|
| Embeddings | `GeneratingEmbeddings` | `EmbeddingsGenerated` | `EmbeddingsFailed` |
| Images | `GeneratingImage` | `ImageGenerated` | `ImageFailed` |
| Audio | `GeneratingAudio` | `AudioGenerated` | `AudioFailed` |
| Transcription | `GeneratingTranscription` | `TranscriptionGenerated` | `TranscriptionFailed` |
| Reranking | `Reranking` | `Reranked` | `RerankingFailed` |
| Classification | `Classifying` | `Classified` | `ClassificationFailed` |

Every failure event carries the same five things: the `invocationId` (matches the starting event), the `provider`, the `model`, the `prompt` and the `exception`.

```php title="app/Listeners/RecordAiFailure.php"
<?php

namespace App\Listeners;

use Illuminate\Support\Facades\Log;
use Laravel\Ai\Events\ClassificationFailed;
use Laravel\Ai\Events\EmbeddingsFailed;

class RecordAiFailure
{
    public function handle(EmbeddingsFailed|ClassificationFailed $event): void
    {
        Log::warning('AI call failed', [
            'invocation' => $event->invocationId,
            'provider' => $event->provider->name(),
            'model' => $event->model,
            'error' => $event->exception->getMessage(),
        ]);
    }
}
```

```php title="app/Providers/AppServiceProvider.php"
use App\Listeners\RecordAiFailure;
use Illuminate\Support\Facades\Event;
use Laravel\Ai\Events\ClassificationFailed;
use Laravel\Ai\Events\EmbeddingsFailed;

public function boot(): void
{
    Event::listen([EmbeddingsFailed::class, ClassificationFailed::class], RecordAiFailure::class);
}
```

<Callout type="heads-up" title="once per attempt, not once per call">

The events fire for **every failed attempt**, including the ones failover recovers from. A call that fails on OpenAI and succeeds on Anthropic dispatches `EmbeddingsFailed` (OpenAI) and then `EmbeddingsGenerated` (Anthropic). Count failures per `invocationId` if you only want to alert when the whole call gave up. Only gateway exceptions trigger them; a `TypeError` in your own code still just throws.

</Callout>

We checked that with `Event::fake()` and a faked 500 from the OpenAI embeddings endpoint: exactly one `EmbeddingsFailed` (provider `openai`, model `text-embedding-3-small`, the same `invocationId` as `GeneratingEmbeddings`) and the `RequestException` rethrown unchanged. A faked 503 from TypeSafe's classification endpoint gave one `ClassificationFailed` carrying a `ProviderOverloadedException`.

## Classification on OpenAI-compatible, TypeSafe and OpenRouter

[Classification](/laravel-ai-structured-output-vue) answers yes/no, multiple-choice and score questions with probabilities instead of generated text. It launched OpenAI-only. Two releases later it runs on four providers:

| Provider | Text | Images | Since |
|---|---|---|---|
| `openai` | Yes | Yes | 1.2.0 |
| `openai-compatible` | Yes | Yes | **1.2.2** |
| `typesafe` | Yes | Yes | text 1.2.0, images **1.2.3** |
| `openrouter` | Yes | Yes (incl. WebP) | text 1.2.0, images **1.2.3** |

### openai-compatible

The `openai-compatible` driver sends the same `/decisions` request the OpenAI provider sends, to your configured `url`. It has **no default classification model**, so set one:

```php title="config/ai.php"
'providers' => [
    'local' => [
        'driver' => 'openai-compatible',
        'url' => env('LOCAL_AI_URL'),
        'key' => env('LOCAL_AI_API_KEY'),
        'models' => [
            'classification' => ['default' => 'decisions-1'], // [!code highlight]
        ],
    ],
],
```

```php title="app/Actions/TriageTicket.php"
use Laravel\Ai\Classification;
use Laravel\Ai\Classification\Boolean;

$result = Classification::of($ticket->body)
    ->question('urgent', new Boolean('Does this request need an immediate response?'))
    ->classify(provider: 'local'); // or ->classify(provider: 'local', model: 'decisions-1')

$result['urgent']->isTrue(threshold: 0.8);
```

In our test the request went to `POST {LOCAL_AI_URL}/decisions` with `Authorization: Bearer <key>` and `model: decisions-1` in the body. Without a model, the call threw an `InvalidArgumentException` ("requires a default classification model") before any HTTP request was made.

<Callout type="tip" title="the default classification provider is TypeSafe">

`config/ai.php` ships with `'default_for_classification' => 'typesafe'`. If you want your OpenAI-compatible gateway (or OpenAI) to answer every `classify()` call, change that key rather than passing `provider:` everywhere.

</Callout>

### Images on TypeSafe and OpenRouter

Pass attachments as the second argument of `Classification::of()`. Give them string keys and your questions can refer to the images by name, on every provider, including after failover:

```php title="app/Actions/InspectProductPhotos.php"
use Laravel\Ai\Classification;
use Laravel\Ai\Classification\Boolean;
use Laravel\Ai\Files\Image;

$result = Classification::of('Two product photos.', [
    'front' => Image::fromPath($front),
    'back' => Image::fromPath($back),
])
    ->question('damaged', new Boolean('Is the product in `front` or `back` damaged?'))
    ->classify(provider: 'openrouter');
```

Each gateway keeps its own wire format, which you only notice when you look at the request. We captured both with `Http::fake()`:

| Provider | Endpoint | How the image travels |
|---|---|---|
| OpenRouter | `POST https://openrouter.ai/api/alpha/decisions` | `state` is `['Two product photos.', 'front:', { type: 'image_url', image_url: { url: 'data:image/png;base64,…' } }]` |
| TypeSafe | `POST https://api.typesafe.ai/v1/systemone` | `assets` keyed by a generated UUID, `state` is `['Two product photos.', 'front: <uuid>']`, plus a `TypeSafe-Danger-Zone-Images: true` header |
| OpenAI | `POST …/decisions` | an inline data URL, preceded by a `name:` text part for named images |

Before 1.2.3, TypeSafe and OpenRouter threw as soon as an attachment was present.

<Callout type="gotcha" title="format checks are shared now">

1.2.3 also unifies the image format check across providers. OpenRouter accepts WebP; a reshaped TypeSafe image state is rejected instead of silently sent. If you built your own `Image` subclass, run your test suite.

</Callout>

## Structured sub-agents inside a streamed parent

Since 1.2.0, a sub-agent used as a tool is **streamed** when its parent streams. Streamed structured output isn't supported, so any sub-agent that implements `HasStructuredOutput` threw, and `AgentTool` handed the parent this tool result:

```text
Agent failed: Streaming structured output is not currently supported.
```

The same agents worked when the parent was prompted instead of streamed, which made the bug look like a flaky model.

```php title="app/Ai/Agents/SupportAgent.php"
class TicketClassifier implements Agent, HasStructuredOutput
{
    // schema(): ['category' => $schema->string()->required()]
}

class SupportAgent implements Agent, HasTools
{
    public function tools(): iterable
    {
        return [new TicketClassifier]; // structured sub-agent as a tool
    }
}

// 1.2.1: the tool result was the failure string. 1.2.2: the real answer.
foreach ((new SupportAgent)->stream('I was charged twice this month.') as $event) {
    //
}
```

[PR #1117](https://github.com/laravel/ai/pull/1117) makes `AgentTool::stream()` call `handle()` for structured sub-agents, the same path the non-streaming flow takes. The sub-agent emits no partial output, but it still runs inside the loop's sub-agent wrapper: `InvokingTool` and `ToolInvoked` fire, and the run stays linked to the parent tool call. Unstructured sub-agents still stream.

<Diagram name="ai-sdk-structured-subagent-stream" alt="A streamed parent agent invokes a sub-agent tool. If the sub-agent has no structured output, it streams as before. If it implements HasStructuredOutput, the SDK now runs it through handle() without streaming, keeps the InvokingTool and ToolInvoked events and the parent linkage, and returns the structured answer to the parent. Before 1.2.2 that branch threw and the parent received an error string." caption="Structured sub-agents take the non-streaming path inside a streamed run." />

This is a stopgap. The author calls real streamed structured output "a much larger change", tracked in [issue #1091](https://github.com/laravel/ai/issues/1091).

## Conversations recover after a failed turn

With `RemembersConversations`, a turn that fails mid tool-loop leaves unanswered tool calls behind. On the next prompt the SDK replays each of them with a placeholder "interrupted" result. That placeholder dropped the stored `result_id`, so on OpenAI, Azure OpenAI and xAI the function call output went out with a `null` `call_id` and **every later prompt in that conversation failed with a 400**.

[#1133](https://github.com/laravel/ai/pull/1133) keeps the id. The fix applies when the history is read, so conversations already stuck recover on their next prompt. No migration, nothing to backfill. Providers that pair tool results by name were never affected and send the same requests as before.

## Laravel 12: conversation ids stay strings

[#784](https://github.com/laravel/ai/pull/784) switched `Conversation` and `ConversationMessage` to the `#[WithoutIncrementing]` attribute. That attribute exists from **Laravel 13.2**; on Laravel 12 it is silently ignored, so both models fell back to `$incrementing = true`. The SDK's own inserts hid it, but `Conversation::create(['id' => 'conversation-1', ...])` came back with the SQLite rowid as its id.

[#1137](https://github.com/laravel/ai/pull/1137) restores `$incrementing = false` on both models. Laravel 13 behaviour is unchanged. If you created conversations through Eloquent on Laravel 12, check for integer ids in `ai_conversations`:

```bash
php artisan tinker --execute="echo Laravel\Ai\Models\Conversation::whereRaw(\"id GLOB '[0-9]*'\")->count();"
```

## Upgrade notes

```bash
composer update laravel/ai
composer show laravel/ai | grep versions   # versions : * v1.2.3
```

<Steps>

1. **Nothing breaks.** Both releases are patches: new events, new provider capabilities and fixes to code that threw before.
2. **Listeners that assume "started means finished"** should handle the new `*Failed` events. Match on `invocationId` to pair them with the starting event.
3. **`openai-compatible` classification** needs `models.classification.default` (or a `model:` argument) or it throws before sending anything.
4. **Streamed parents with structured sub-agents:** remove any workaround that wrapped the sub-agent in a plain tool or forced `prompt()`.
5. **Laravel 12 apps with conversations** created through Eloquent: audit the ids (above). Laravel 13 apps have nothing to do.

</Steps>

## Try it yourself

<TryIt title="Assert the failure event in one Pest test">

```php title="tests/Feature/EmbeddingsFailedTest.php"
use Illuminate\Http\Client\RequestException;
use Illuminate\Support\Facades\Event;
use Illuminate\Support\Facades\Http;
use Laravel\Ai\Embeddings;
use Laravel\Ai\Events\EmbeddingsFailed;

test('a failed embeddings call dispatches EmbeddingsFailed', function () {
    config(['ai.providers.openai.key' => 'test']);
    Event::fake([EmbeddingsFailed::class]);
    Http::fake(['api.openai.com/*' => Http::response(['error' => ['message' => 'boom']], 500)]);

    expect(fn () => Embeddings::for(['Napa Valley has great wine.'])->generate())
        ->toThrow(RequestException::class);

    Event::assertDispatchedTimes(EmbeddingsFailed::class, 1);
    Event::assertDispatched(EmbeddingsFailed::class, fn (EmbeddingsFailed $e) => $e->provider->name() === 'openai'
        && $e->model === 'text-embedding-3-small'
        && $e->exception instanceof RequestException);
});
```

Swap `Embeddings::for()` for `Classification::of()`, the event for `ClassificationFailed` and the status for 503, and you get a `ProviderOverloadedException` on the event instead. Note that `Embeddings::for()` takes an **array** of inputs; `Str::of('…')->toEmbeddings()` is the one-string shortcut.

</TryIt>
